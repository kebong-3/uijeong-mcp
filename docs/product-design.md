# 지방의회 MCP 제품 설계 및 선행사례 검토

검토일: 2026-09-17. 기준자료: 사용자 제공 v1.1 소스, v1.2 분석·수정·검증 보고서. 이 문서는 서비스 방향과 이번에 구현한 업무 모듈의 범위를 설명한다.

## 1. 개발 취지와 제품 정의

**지방의회에 축적된 정책 논의를 행정의 설명 책임과 개선에 연결하는 근거 중심 업무 도구.** 담당자는 회의록을 찾고, 당시 질문과 답변을 확인하고, 이번에 준비할 자료와 후속 확인사항을 정리할 수 있다. 의회도 동일한 공개 근거를 통해 질의 취지와 후속 설명을 확인할 수 있는 구조를 지향한다.

서비스 명칭은 `지방의회 MCP — 의정근거`를 권장한다. 핵심 설명은 **“의회 논의의 맥락을 확인하고, 근거 있는 답변과 후속조치를 준비합니다.”**로 제안한다. 명칭과 설명은 기획 제안이며 등록·상표 확인 결과가 아니다.

## 2. 이미 있는 서비스와 차별화 방향

| 확인한 서비스 | 운영 주체·확인 내용 | 이번 MCP의 설계상 차별화 목표 |
|---|---|---|
| [지방의정포털 CLIK](https://clik.nanet.go.kr/potal/guide/siteUseGuidance.do) | 국회도서관. 지방의회 의안·회의록·정책자료 통합검색 및 원문 이용 안내 | 공식 API의 검색 결과를 문서·발언·질의답변·후속조치 후보로 구조화하여 업무 준비에 사용 |
| [지방의회 회의록 검색](https://reforminst.org/council) | 개혁연구원. 키워드가 정확히 일치하지 않는 관련 회의 검색과 회의록 DB에 근거한 AI 질문 메뉴 확인. 일부 의회의 자료 미등록·수집 실패 가능성도 안내 | 정당·의원별 분석을 제품 목표로 삼지 않고, 행정 업무의 근거 재현·답변 준비·조치 증빙 확인에 집중 |
| [예산군의회 자료실](https://www.councilyesan.go.kr/) | 지방의회 공식 홈페이지. 질문답변 검색·발언자별 검색·부록·행정사무감사·군정질문 자료 등 메뉴 확인 | 의회별로 분산된 자료를 동일한 근거 형식으로 다루고, 원문을 확인한 범위와 못 읽은 범위를 함께 제시 |

따라서 **‘지방의회 검색이나 회의록 AI가 처음 등장했다’고 홍보할 근거는 없다.** 위 비교는 공개 화면과 안내에 따른 기능 비교이며 경쟁 서비스의 내부 알고리즘·정확도·응답시간을 시험한 결과가 아니다. 이번 MCP가 기존 서비스보다 우수하다는 실증 결과도 아직 없다.

CLIK의 [Open API 안내](https://clik.nanet.go.kr/potal/guide/resourceCenter.do)는 데이터 연동의 출발점이다. 안내 화면마다 의회 수·분류의 표기 시점이 다를 수 있으므로 홈페이지 숫자, 내부 등록 목록 수, 실제 API에서 조회되는 자료 수, 직접 어댑터가 검증된 의회 수를 동일하게 표시하지 않는다.

## 3. 실제 업무 흐름

| 업무 | 입력 | 결과물 | 담당자가 확인할 사항 |
|---|---|---|---|
| 예산·결산 심의 준비 | 주제·의회·위원회·명시적 조회기간 | 당시 질문·답변 원문, 기준일·회계연도 확인 목록, 답변 작성 틀 | 최신 예산서·결산서의 수치와 근거 |
| 행정사무감사 준비 | 주제·부서·조회기간 | 근거 질문별 준비 후보, 유사 질문이 나온 제공 문서 수 | 질문 취지, 금년 변경사항·설명자료 |
| 부서 인수인계 | 해당 업무의 과거 논의·후속조치 후보 | 원문 문장·조건·기한·증빙 확인 칸 | 현재 담당부서와 실제 이행자료 |
| 타 의회 사례 조사 | 정책 주제·비교 의회·기간 | 출처가 연결된 질문과 당시 답변 | 재정·조직·조례·시점의 차이 |
| 5분자유발언 후속 검토 | 발언 원문 | 질의응답과 구분한 발언 근거 | 별도 서면답변·조치계획 존재 여부 |

권장 사용 예:

- “2023~2025년 서구의회 성인지예산 관련 논의를 연도별로 확인하고, 질문·당시 답변·이번 심의 준비자료를 구분해줘.”
- “주민참여예산 교육에 관한 질문을 정리하되, 교육 참여자 감소와 성과지표 달성을 별개로 검토할 자료를 알려줘.”
- “이전 답변 중 자료제출·검토·시행 의사 후보를 원문 그대로 제시하고, 실제 조치 여부는 증빙 미확인으로 남겨줘.”
- “5분자유발언에 회의 중 답변이 없다는 이유로 미답변이라고 판정하지 말고, 후속 서면자료를 확인할 항목을 정리해줘.”

## 4. 의회와 집행부가 함께 사용할 표현 원칙

| 대상 | 원칙 |
|---|---|
| 분석 단위 | 정책·사업·안건·질문·답변·후속 증빙을 기준으로 정리 |
| 발언 인용 | 비판적 표현도 원문 그대로 보존. 인용을 임의로 완곡하게 바꾸지 않음 |
| 작성 문안 | 질문의 정책 쟁점을 설명하고 확인된 현황·개선계획을 공무원 문체로 작성 |
| 사람 정보 | 원문 출처에 필요한 발언자 표기는 유지. 성향·공격성·영향력 점수·취약점·정치적 대응전략은 생성하지 않음 |
| 질문 후보 | 기존 질문을 근거로 준비할 질문을 제안. 특정 의원의 미래 질문이나 확률로 제시하지 않음 |
| 후속조치 | 검토 의사와 확정 시행을 구분. 발언만으로 이행·미이행을 판정하지 않음 |
| 부서 이력 | 회의 당시 직함과 현재 담당부서를 구분. 조직개편 이력 없이 자동 배정하지 않음 |

‘의원님 말씀을 모두 반영하겠다’와 같은 무조건적 약속도 자동 생성하지 않는다. 확인된 사실, 검토가 필요한 부분, 확정 가능한 조치, 조건과 기한을 구분하여 작성하게 한다.

## 5. 이번에 구현한 업무 함수

파일: `workflow_core.py`. 외부 AI 호출·네트워크 요청·파일 쓰기 없이 `evidence_core.record_events()`의 결과를 받아 처리하는 순수 함수이다.

```python
build_briefing(records, *, topic, council=None, coverage=None)
build_faq_candidates(records, *, topic, coverage=None, limit=10)
build_followup_ledger(records, *, coverage=None)
```

여기서 `records`는 원문 record가 아니라 **근거 event 목록**이다. `topic`과 `council`은 준비자료의 요청 맥락이며 이 함수 자체가 검색·필터링을 다시 수행하는 것은 아니다. 검색·기간·위원회·부서 필터는 앞단의 수집·근거 계층에서 수행한다.

| 함수 | 실제 구현 | 해석상 한계 |
|---|---|---|
| `build_briefing` | 질문·답변·기타 발언·후속조치 후보·준비 질문·답변 작성 틀 통합 | 최신 현황은 자동 작성하지 않음. 현재 사실과 이행 증빙은 별도 확인 |
| `build_faq_candidates` | 공백·Unicode 표기를 정규화한 동일 질문별 묶음, 제공 문서 수, 자료준비 분야·질문 제안 | 의미상 유사한 질문의 군집화 기능은 아님. 빈도는 입력 문서 범위이고 전국 빈도·질문 예측치가 아님 |
| `build_followup_ledger` | 후보 문장 원문 대조, 발언 위치, 원문 조건·기한, 증빙 확인 칸 | 원문에서 대조되지 않는 문장·조건·기한은 확정 인용하지 않음. 달력 마감일·담당부서·완료 여부는 자동 추정하지 않음 |

각 인용에는 문서·발언 식별자, 출처 주소와 확인 상태, 본문·발언 해시, 회계연도 필드를 보존한다. 제공 문장 자체의 SHA256도 추가한다. 합성자료·사용자 제공·로컬 보관자료를 중첩된 공식 출처 표기만으로 승격하지 않는다. 원문 발언의 비판적 문구나 공백을 임의로 수정하지 않는다.

이 함수들은 `current_answer=null`, `calendar_due_date=null`, `owner_department=null`, `fulfillment_status=EVIDENCE_NOT_VERIFIED`를 기본값으로 둔다. 이는 현황을 모를 때 빈칸을 임의의 사실로 채우는 문제를 막기 위한 업무 계약이다. 후속조치 결과를 영속적으로 등록하거나 실제 완료 증빙을 판정하는 관리 시스템은 별도 구현 범위다.

## 6. 기존 v1.2 피드백과 반영 관계

| 기존 보고서 요구 | 이번 업무 계층 반영 |
|---|---|
| 질문·답변·보고 구분 | 근거 계층의 질문·답변만 FAQ로 사용, 보고 발언을 질문으로 생성하지 않음 |
| 합성자료 출처 문제 | event 또는 citation에 합성 표기가 있으면 합성자료 유지 |
| 회의연도와 회계연도 혼동 | 입력에 명시되지 않은 회계연도는 null 유지 |
| 같은 날짜·위원회 중복 오판 | 동일 날짜나 문구만으로 문서 삭제하지 않고 완전히 같은 입력 event 복사본만 제거 |
| 약속을 완료·미이행으로 읽는 문제 | 후속조치 후보와 후속 증빙 상태 분리 |
| 검토·시행 및 조건·기한 구별 | 근거 계층의 분류를 후보로 표시하고 조건·기한은 인용문 대조 |
| 근거 위치 재현 | 문서·발언·문자 위치·인용 해시와 출처 확인 상태 유지 |
| 오류·부분·미발견 혼동 | 상류 범위 정보 보존. 상류 실패 뒤 남은 자료는 PARTIAL로 표시 |

파서·출처별 검색·이어읽기·배포 버전·보안·호출예산은 다른 구현 계층의 검증사항이다. 이 모듈의 테스트 통과를 전체 운영환경 검증으로 설명하지 않는다.

## 7. 4개 검토 담당 간 논의

사용자 요청에 따라 제품·데이터 소스·근거 엔진·운영 보안의 네 담당으로 작업을 나누고 메시지를 통해 계약을 조율했다.

| 담당 | 제안·검토 의견 | 반영 결정 |
|---|---|---|
| 제품·업무 흐름 | 공무원에게 즉시 유용한 산출물이 필요하지만 자동 답변이 과거 사실을 현재로 옮길 수 있음 | 당시 근거와 현재 답변 작성 칸 분리. 자료준비 항목을 함께 반환 |
| 근거 엔진 | 원문 record와 event를 구분하고 문답·후속조치의 발언 위치를 공유해야 함. FAQ 분모와 확인 범위를 함께 제시할 필요 | event 목록으로 인터페이스 확정. 후속조치 excerpt·turn_index·char_start/end 추가 연계. 식별 가능한 입력 문서 수와 출처 미식별 건수를 분리 |
| 데이터 소스 | CLIK와 의회 홈페이지의 최신 자료 시점이 다르고 안내 페이지 숫자도 일치하지 않을 수 있음 | 전체 의회 수·등록 목록·실제 수집·직접 어댑터 검증 범위를 분리하여 안내 |
| 운영 보안 | 정적 Bearer는 OAuth가 아니며 SQLite 공통 예산은 같은 파일을 공유하는 환경에 한정됨 | 설치 설명에 범위를 명시하고 ChatGPT 앱 자동 호환·분산 호출량 관리를 구현했다고 표현하지 않음 |

인증키를 대화에 붙여 넣게 하지 않고 운영 환경변수에서 사용한다. 실제 API 연결 확인은 키 보유 여부와 네트워크·상류 응답을 구분해서 설명해야 한다. 비공개 입력의 보관은 명시적으로 켠 경우에만 허용하는 운영 방향을 사용한다.

## 8. 검증과 후속 평가

`python -m pytest tests/test_workflows.py -q`에서 35건의 합성 입력·계약 시험을 통과했다. 실제 `evidence_core.make_record → record_events → build_briefing` 연결도 포함한다. 주요 검증은 정확 인용·출처 유형 하향 보존·회계연도 비추정·미연결 답변·후속 기한 비추정·허위 후보 인용 차단·부분 오류·복사본 중복·입력 불변성이다.

다음 실증 단계에서는 공무원이 실제 사용한 업무 질문을 기준 데이터로 구성하고, 사람이 정답 문서·발언·질의답변 연결을 확정해야 한다. 평가지표는 근거 도달률, 관련 발언 누락률, 문답 오연결률, 출처 재현률, 준비시간, 호출 수·지연시간으로 제안한다. 정확도나 업무시간 절감 비율은 측정 전 홍보 수치로 만들지 않는다.

## 9. 2.3.0 설계 추가 — 진입 단위를 주제어에서 부서로

2.2까지의 진입점은 검색어였다. 검색어 진입은 **담당자가 쟁점을 이미 안다**는 전제를 깔고 있는데, 의회 대응이 가장 어려운 사람(신규 발령자, 소관 변경 부서)은 그 전제를 만족하지 못한다. 이들이 확실히 아는 것은 자기 부서 이름뿐이다. 2.3은 진입 단위를 한 칸 낮춰 부서명만으로 시작할 수 있게 했다.

| 설계 문제 | 관측 | 채택한 방식 |
|---|---|---|
| 부서명이 질의 본문에 없음 | 부서명을 본문 주제어로 거르면 결과 0건 | 부서명은 **검색어**로만 쓰고, event 단계에서는 본문 필터를 걸지 않은 뒤 발언자 직함의 부서 어간으로 분류 |
| 과장 대신 팀장이 답하는 대리답변 | 직함 완전일치로 거르면 누락 | `미래전략과장`·`미래전략팀장`을 같은 어간으로 축약해 일치 |
| 조직개편으로 부서명이 바뀜 | 서버가 개편 이력을 추정하면 근거 없는 확장이 됨 | 추정하지 않고 `extra_terms`로 담당자가 과거 명칭을 지정 |
| 답변이 확인 범위 밖에 있음 | '답변 없음'으로 적으면 사실과 다른 판정이 됨 | `unanswered`는 `NOT_LINKED_IN_SCOPE`로 표기하고 한계 문구를 함께 반환 |
| 반복 집계가 예측으로 읽힘 | "다음에도 나올 질문"으로 오해될 여지 | 연도·회의 단위로만 세고, 질의 성격 발언만 집계하며, 출력에 '예측 아님'을 명시 |
| 서식 칸을 AI가 채움 | 검토의견을 자동 작성하면 책임 소재가 흐려짐 | 판단이 필요한 칸은 비운 채 `담당자 확인 필요`로 남기고 문장을 생성하지 않음 |

의원 개인 단위 집계를 만들지 않는다는 기존 원칙은 세 도구 모두에 그대로 적용했다. 반복 쟁점은 '누가 몇 번 말했는가'가 아니라 '몇 개 연도에 걸쳐 나왔는가'로만 센다.
