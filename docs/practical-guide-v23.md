# 의정소통 MCP 2.3 — 부서에서 시작하는 의회 대응

2026년 9월 20일 · v2.2.0을 기반으로 부서 단위 실무 흐름을 더한 소스·로컬 검증본

## 왜 도구를 더했나

2.2까지의 흐름은 **담당자가 무엇을 찾아야 하는지 이미 아는 경우**에 잘 작동했습니다. `keyword="성인지예산"`으로 검색하려면 그 사업이 쟁점이라는 사실을 먼저 알아야 합니다. 그런데 의회 대응이 가장 어려운 사람은 정기인사로 막 발령받은 담당자, 처음 업무보고에 들어가는 신규 임용자, 소관이 바뀐 부서입니다. 이들이 가진 정보는 사업명이 아니라 **자기 부서 이름 하나**입니다.

그래서 2.3은 진입점을 하나 낮췄습니다.

| 담당자가 아는 것 | 2.2에서 가능한 것 | 2.3에서 가능한 것 |
|---|---|---|
| 사업명·쟁점 | 근거 검색 → 답변카드 | 동일 |
| 부서 이름만 | (검색어를 추측해야 함) | 부서명만으로 우리 과가 받은 질의·답변·후속조치 |
| 아무것도 | — | 부서 브리핑 → 반복 쟁점 → 서식 배치까지 한 흐름 |

## 더한 도구 3개

### 1. `council_department_brief` — 부서 기준 진입

부서명만 넣으면 그 부서가 의회에서 받은 질의와 답변, 후속조치 후보를 모읍니다.

기술적으로 이 도구가 푸는 문제는 하나입니다. **부서명은 질의 본문에 나오지 않습니다.** 위원이 "노인복지관 급식 위생점검은 어떻게 합니까"라고 물을 때 '노인복지과'라는 말은 어디에도 없습니다. 부서명은 답변한 사람의 직함, 즉 `○노인복지과장 이가상`에 나타납니다. 그래서 본문 주제어로 거르면 결과가 0건이 됩니다. 이 도구는 부서명으로 회의록을 찾은 뒤, **발언자 직함의 부서 어간으로** 소관을 가릅니다.

- `미래전략과장`과 `미래전략팀장`을 같은 부서로 봅니다. 과장 대신 팀장이 답한 **대리답변을 놓치지 않습니다.**
- 조직개편 전 명칭이나 약칭은 `extra_terms`로 최대 2개 더합니다. 개편 이력을 서버가 추정하지 않습니다.
- 결과는 세 갈래입니다. `answered`(우리 부서가 답한 질의), `unanswered`(부서가 거론됐으나 이번 확인 범위에서 답변이 연결되지 않은 질의), `other_mention`(다른 발언자가 답한 거론 건).

`unanswered`는 **'이번 확인 범위의 결과'이지 '답변하지 않았다'는 판정이 아닙니다.** 답변이 다른 회의록에 있거나, 수집 한도 밖에 있거나, 서면으로 갈음됐을 수 있습니다. 이 구분은 표기에 그대로 남습니다.

### 2. `council_recurring_issues` — 해마다 반복되는 요구

행정사무감사와 업무보고 준비의 출발점은 "작년에도 지적받은 것이 무엇인가"입니다. 이 도구는 회의연도를 나눠 같은 한도로 조회한 뒤, 주제어가 **몇 개 연도에 걸쳐** 등장했는지 셉니다.

집계 원칙 세 가지를 코드에 고정했습니다.

- **질의 성격 발언만 셉니다.** 답변에 나온 말을 의회의 요구로 세면 방향이 뒤집힙니다. "분기마다 점검하겠습니다"는 집행부의 말이지 의회의 요구가 아닙니다.
- **집계 단위는 연도와 회의입니다.** 어느 의원이 몇 번 말했는지는 세지 않습니다. 의원 개인 단위 집계는 만들지 않았습니다.
- **결과는 '반복 확인'이며 예측이 아닙니다.** 다음 회기에 나올 질문의 확률로 표시하지 않고, 출력의 한계 문구에 그대로 적습니다.

`원인`·`규모`·`현황`처럼 내용이 없는 말은 집계에서 뺍니다. 주제어가 아니라 서술어이기 때문입니다.

### 3. `council_format_worksheet` — 기관 서식 칸에 배치

확인된 발언과 담당자 제공자료를 기관 회의자료 서식 칸에 넣고, 문서에 바로 붙여넣을 본문(`plain_text`)을 만듭니다.

| 서식 | 칸 구성 |
|---|---|
| 5분자유발언_회의자료 | 개요 / 현 실태 / 검토결과 / 행정사항 |
| 구정질문_답변서 | 질의요지 / 현황 / 답변요지 / 향후계획 |
| 행정사무감사_답변카드 | 지적사항 / 현황 / 조치계획 / 참고 |
| 1페이지_검토보고 | 추진배경 / 주요내용 / 검토의견 / 조치사항 |

핵심 규칙은 **비워 두는 것**입니다. 검토의견·답변요지처럼 판단이 필요한 칸에는 문장을 만들어 넣지 않고 `담당자 확인 필요`로 남깁니다. 근거가 들어간 칸은 회의록 원문, 제공자료 칸은 `USER_PROVIDED`로 출처를 구분해 표시합니다. 회의일은 `2026.12.25.`처럼 공문서 표기로 쓰고, 두 글자 항목명은 `개    요`처럼 네 글자 폭으로 벌려 적습니다. 이미 띄어 쓴 `현 실태`는 기관 표기를 그대로 둡니다.

기관마다 서식이 다르므로 **제출 전 소속 기관 양식과 대조해야 합니다.** 이 도구는 배치를 돕는 것이지 결재 문서를 완성하지 않습니다.

## 바로 써 볼 요청문

1. "광주 서구의회에서 우리 노인복지과가 받은 질의와 답변을 정리해 줘. 최근 2년치면 돼."
2. "우리 과에 해마다 반복해서 나오는 지적이 뭐야? 최근 3개 회의연도로 확인해 줘."
3. "방금 나온 첫 번째 질의로 행정사무감사 답변카드 서식을 만들어 줘. 현황 수치는 내가 줄게."
4. "이 부서가 약속한 자료제출 건만 따로 뽑아 줘. 기한이 원문에 적혀 있는 것과 없는 것을 구분해 줘."
5. "조직개편 전에는 '기획감사실'이었어. 예전 이름도 같이 넣어서 찾아 줘."

기본 의회는 광주 서구입니다. 다른 기관은 "서울 광진구", "부산 서구"처럼 시·도와 시·군·구를 함께 지정하세요. '서구'만으로 지역을 임의 확정하지 않습니다.

## 부서 담당자 권장 흐름

1. `council_department_brief(department="노인복지과")` — 우리 과가 받은 것 전체를 먼저 본다.
2. `council_recurring_issues(department="노인복지과", years=3)` — 그중 해마다 반복된 것을 추린다.
3. `council_get_evidence(snapshot_id=...)` · `council_read_source(ref=docid)` — 실제 원문으로 확인한다.
4. `council_format_worksheet(...)` — 기관 서식 칸에 배치한다.
5. `council_review_answer` · `council_check_figures` — 제출 전 수치와 표현을 점검한다.

1번의 결과에는 다음 단계 인자가 들어 있어, 연결된 AI가 흐름을 이어가도록 되어 있습니다. 준비표(`council_plan_session`)로 회기 일정을 먼저 잡고 이 흐름에 들어가도 됩니다.

## 이 버전이 하지 않는 것

- 의원 개인의 성향·공격성·질문 빈도를 집계하지 않습니다. 세 도구 어디에도 의원 단위 통계가 없습니다.
- 다음 회기 질문을 예측하지 않습니다. 반복 집계는 지나간 회의록의 확인입니다.
- 판단이 필요한 서식 칸을 대신 채우지 않습니다.
- 후속조치의 이행 여부를 판정하지 않습니다. `EVIDENCE_NOT_VERIFIED`는 '증빙 미확인'이지 '미이행'이 아닙니다.
- 조직개편 이력을 추정하지 않습니다. 과거 부서명은 담당자가 지정합니다.
- 담당자가 제공한 부서 자료와 초안을 서버에 저장하지 않습니다.

## 설치·교체

ZIP의 전체 소스를 시험 폴더에 풀고, `UIJEONG_PROFILE=work`로 실행한 뒤 `council_status()`에서 **버전 2.3.1과 도구 14개**를 확인합니다. 신규 파일만 복사하면 등록 계층과 프로필 정의가 빠집니다. 기존 CLIK_API_KEY는 그대로 유지하며, 이번 기능에 추가 API 키는 필요하지 않습니다. 자세한 순서는 README와 v2.2 안내서를 따릅니다.

## 2.3.1 — 운영 중 발견한 것

무료 플랜(메모리 512MB·CPU 0.1)에 올려 실제로 써 보니, 회의록을 계속 열다 보면 프로세스가 배포 플랫폼의 상태점검에 응답하지 못하고 재시작되는 일이 있었습니다. 코드에 두 가지 원인이 있었습니다.

첫째, 회의록 캐시에 상한이 없었습니다. 캐시 한 항목은 회의록 본문 전체입니다. 홈페이지 어댑터는 상세 회의록을 7일간 무제한으로 들고 있었고, CLIK 캐시는 800건까지 쌓였습니다. 작은 인스턴스에서는 쓸수록 메모리가 차오르는 구조였습니다. 세 캐시 모두 한도에 닿으면 가장 오래된 항목부터 비우도록 바꾸고 기본값을 낮췄습니다.

둘째, 긴 회의록 파싱이 이벤트 루프에서 돌았습니다. 한 건에 0.1초 안팎이 걸리는데, CPU 0.1개짜리 인스턴스에서 여러 건을 연속 처리하면 그동안 들어온 연결과 상태점검이 전부 대기합니다. 본문 파싱을 별도 스레드로 옮겨, 파싱 중에도 서버가 응답할 수 있게 했습니다.

검사도 함께 넣었습니다. 회의록 30건을 연속으로 열어도 캐시가 한도 안에 머무는지, 긴 회의록 한 건을 파싱하는 동안 다른 작업이 진행되는지 확인합니다. 두 번째 검사는 파싱을 이벤트 루프로 되돌리면 실제로 실패합니다(진행 0회).

무료 플랜은 15분 유휴 시 잠들고 재기동이 느립니다. 여러 사람이 상시로 쓸 계획이라면 유료 플랜이 맞습니다.
