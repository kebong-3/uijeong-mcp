# 지방의회 MCP 2.5.0 사용·교체 안내

## 1. 무엇이 달라졌나요?

회의록을 찾아 주는 기능에서 한 단계 더 나아가 **공무원이 답변자료를 준비하고 검수하는 흐름**을 추가했습니다.

| 하고 싶은 일 | 새 버전의 처리 |
|---|---|
| “천원국시 의회 답변을 준비해 줘” | 기간 안의 질의답변을 모으고, 원문 출처·현재 자료·확인할 사항을 함께 정리 |
| “이 답변에 근거 없는 내용이 있어?” | 문장마다 원문을 연결해 발췌 변형·미연결 주장·수치 누락 등을 표시 |
| “사업비가 얼마나 늘었어?” | 본예산/최종예산, 연간/누적, 대상과 단위를 대조하고 비교 가능한 경우 계산 |
| “예전 답변과 지금 설명이 달라?” | 두 발언을 나란히 놓고 수치·조건·부정 표현을 확인. 모순이나 미이행은 자동 단정하지 않음 |

완성된 답변 문장은 연결된 AI가 근거를 읽고 작성합니다. 서버가 근거 없는 정책 판단이나 현재 실적을 만들어 넣지 않습니다. 새 OpenAI·Gemini API 키는 필요하지 않습니다.

## 2. 교체 순서

1. 현재 GitHub 커밋을 기록하고 운영 설정·저장소를 백업합니다.
2. ZIP을 풀고 **`uijeong-mcp` 폴더 안의 파일 전체**를 기존 프로젝트 루트에 반영합니다. `uijeong_mcp.py`만 바꾸면 새 모듈을 불러올 수 없습니다.
3. 기존 `.env`, 실제 키, 운영 `state` 데이터는 공개 GitHub에 올리지 않습니다.
4. 개발 환경에서 아래 명령을 실행합니다.

```bash
python -m pip install -r requirements.txt pytest==8.4.2
python -m pytest -q
python tests/protocol_smoke.py
python scripts/check_config.py --manifest
```

5. Render 설정의 `UIJEONG_PROFILE`을 `work`로 둡니다. 현재 정상 사용 중인 인증 설정과 `CLIK_API_KEY`는 유지합니다.
6. 새 커밋을 배포하고, 클라이언트 연결에서 도구 명세를 갱신한 다음 새 대화로 확인합니다. 단순 서버 재시작만으로 새 GitHub 소스가 반영되는 것은 아닙니다.

## 3. 정상 적용 확인

`council_status(live=False)` 결과에서 아래를 확인합니다.

| 항목 | 예상 값 |
|---|---|
| version | `2.5.0-rc.1` |
| profile | `work` |
| tool_count | `18` |
| release_verification.status | `MATCH` |
| runtime_fingerprint | 패키지 `release_manifest.json` 값과 일치 |

도구 목록에는 `council_prepare_response`, `council_audit_claims`, `council_compare_metrics`, `council_compare_evidence`가 추가됩니다. core 프로필에는 나타나지 않습니다.

`council_status(live=True)`는 CLIK·홈페이지의 실제 조회를 따로 검사합니다. `/healthz`의 200 응답만으로 인증과 회의록 조회까지 성공한 것은 아닙니다.

승인된 관리 환경에서 접속 토큰을 `UIJEONG_VERIFY_TOKEN` 환경변수에 설정했다면 다음도 실행할 수 있습니다. 실제 주소로 바꾸고, 토큰을 명령행 인자나 URL에 붙이지 않습니다.

```bash
python scripts/verify_deployment.py --url https://YOUR-SERVICE.onrender.com/mcp
```

## 4. 기존 401 오류가 남아 있다면

401은 MCP 접속 인증 문제입니다. CLIK 키 오류와 다릅니다. 코드 교체만으로 클라이언트가 접속 토큰을 전달하게 되지는 않습니다.

- 정적 Bearer를 전달하는 기존 연결이면 `UIJEONG_AUTH_MODE=bearer`와 기존 비밀 토큰 설정을 사용합니다.
- 외부 OAuth 인증서버를 사용한다면 `UIJEONG_AUTH_MODE=oauth`와 기존 issuer·audience·introspection 설정을 유지합니다. 이 패키지는 외부 인증서버를 새로 만들어 주지 않습니다.
- 두 모드의 상세 설정과 상호 배제는 `docs/UPGRADE_v240_KO.md`의 인증 설정을 따릅니다. 새 버전은 이 설정 계약을 바꾸지 않았습니다.

실제 키를 대화창에 붙여 넣을 필요는 없습니다.

## 5. 바로 써 볼 요청

> 광주 서구 천원국시 사업의 2024-01-01부터 2026-09-20까지 질의답변을 찾아서 우리 부서의 행정사무감사 답변 준비자료를 만들어 줘. 과거 발언, 현재 자료, 추가 확인사항을 구분하고 출처를 붙여 줘. 검색이 덜 된 구간도 표시해 줘.

작성부서명은 실제 부서명으로 지정합니다. 조회기간 예시는 목적에 맞게 바꾸세요. `department`는 작성부서로, 해당 사업의 소관을 자동 확정하거나 답변자를 필터링하지 않습니다. 소관별 과거 답변 분류는 기존 `council_department_brief`를 사용합니다.

> 내 답변 초안을 문장별로 근거와 연결해 검수해 줘. 자료에 없는 수치뿐 아니라 근거 없는 “문제없음·완료·효과 입증” 같은 주장도 확인해 줘.

`facts`로 붙이는 현황자료에는 **문서명·쪽수/문서번호·기준일·단위·회계연도**를 함께 넣습니다. 원문이 없는 숫자만 제공하면 검수 근거가 부족합니다.

## 6. 운영에서 마지막으로 확인할 것

- 실제 의회 회의록 3건 이상을 열어 회의일·발언자·질문과 답변의 연결·조건을 대조합니다.
- 감사 결과보고서, 현재 사업자료, 처리결과 증빙은 별도로 대조합니다.
- `next_actions`가 남았으면 전체 조사가 완료됐다고 표현하지 않습니다.
- OAuth 이용자별로 스냅샷 접근이 분리되는지 운영 계정으로 확인합니다. 정적 Bearer 하나를 여러 사람이 공유하면 동일한 인증 주체 범위입니다.
- `UIJEONG_STATE_DB`를 영속 경로에 두지 않으면 재배포 뒤 공개 근거를 재수집할 수 있습니다.

문제 발생 시 기록한 이전 커밋과 설정으로 되돌립니다. 이번 버전은 SQLite 테이블 구조를 변경하지 않았습니다. 이전 스냅샷을 사용할 때도 기존 사용자 범위·유효기간은 적용됩니다.
